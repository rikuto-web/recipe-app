# 非機能要件

機能要件で定義した操作を、どの品質で提供するかを定める。

## 1. 対象環境


| 項目      | 開発                            | 本番                                         |
| ------- | ----------------------------- | ------------------------------------------ |
| フロントエンド | `http://localhost:5173`       | fe-vm 上。nginx 配下                           |
| バックエンド  | `http://localhost:8080`       | api-vm 上。本番では fe-vm の nginx が `/api` をプロキシ |
| データベース  | リポジトリ配下の SQLite ファイル          | api-vm ディスク上の SQLite ファイル                  |
| 想定ブラウザ  | 最新の Chrome / Firefox / Safari | 同左                                         |

開発環境は Docker Compose で FE / API / DB を起動してもよい（任意）。詳細は [システム構成 §2.1](07-architecture.md#21-docker-compose開発のみ任意)。
## 2. 性能


| ID      | 要件                                                     |
| ------- | ------------------------------------------------------ |
| NFR-P01 | ローカルでは一覧・詳細 API のレスポンスを、データ数十件規模で 200ms 程度に収めることを目標とする |
| NFR-P02 | 一覧は初回表示で全件取得してよい。ページネーションは今回の必須としない（100 件を超える見込みは低い）   |
| NFR-P03 | 按分計算はクライアント側で行い、人数変更のたびに API を呼ばない                     |


## 3. 可用性・耐障害


| ID      | 要件                                                  |
| ------- | --------------------------------------------------- |
| NFR-A01 | 開発・学習用途のため、冗長化（複数 VM）は最低限とする                        |
| NFR-A02 | API プロセス停止時は nginx または画面側で到達不能を伝え、フロントが例外で落ちたままにしない |
| NFR-A03 | SQLite ファイル破損に備え、運用手順としてファイルコピーによるバックアップ方針を持つ       |


冗長化（複数 VM による FE/API 分離）は行うが、各層の待機系は設けない。fe-vm または api-vm の障害は許容する。SLA は設定しない。

## 4. セキュリティ


| ID      | 要件                                                                |
| ------- | ----------------------------------------------------------------- |
| NFR-S01 | ブラウザから SQLite へ直接接続しない。すべてのデータ操作は API 経由とする                       |
| NFR-S02 | 開発時は CORS で許可オリジンを `http://localhost:5173` に限定する。本番は実際のオリジンのみ許可する |
| NFR-S03 | 入力はサーバー側で長さ・型・件数を検証する。SQL はプレースホルダを使い、文字列連結でクエリを組まない              |
| NFR-S04 | 認証はないが、本番の SSH は管理者 IP に制限する。80 / 443 以外のアプリポートは NSG で公開しない       |
| NFR-S05 | シークレット（OCI API キー、SSH 秘密鍵）はリポジトリに含めない                             |


画像もユーザー登録もないため、オブジェクトストレージやセッション管理は対象外とする。

## 5. 保守性・変更容易性


| ID      | 要件                                                           |
| ------- | ------------------------------------------------------------ |
| NFR-M01 | フロント（見せ方）とバック（保存・検証）と DB（永続化）の責務を分ける                         |
| NFR-M02 | API は REST の資源名と HTTP メソッドで操作を表す                             |
| NFR-M03 | データアクセスは SQL を明示し、SQLite 固有機能への依存を最小にする（将来の PostgreSQL 移行余地） |
| NFR-M04 | インフラは Terraform で VCN / Compute / NSG を定義し、コンソールの手動差分を減らす    |


## 6. 運用


| ID      | 要件                                                        |
| ------- | --------------------------------------------------------- |
| NFR-O01 | 本番プロセスは systemd 等で常駐させ、VM 再起動後に自動起動する                     |
| NFR-O02 | API は構造化ログ（少なくとも method, path, status）を標準出力またはファイルへ出す     |
| NFR-O03 | デプロイは SSH 後のビルド成果物配置を基本とする。CI/CD は必須にしない                  |
| NFR-O04 | Always Free の範囲に収まるシェイプ（例: Ampere A1 の空き枠）を使う。課金リソースは作らない |


## 7. 互換性・データ


| ID      | 要件                                       |
| ------- | ---------------------------------------- |
| NFR-C01 | 文字コードは UTF-8                             |
| NFR-C02 | API の入出力は JSON                           |
| NFR-C03 | 日時は UTC で保存し、画面では利用者のロケールで表示してよい         |
| NFR-C04 | マイグレーション手段を用意し、スキーマ変更を手作業の SQL 実行だけに頼らない |


## 8. アクセシビリティ・UX（最低限）


| ID      | 要件                    |
| ------- | --------------------- |
| NFR-U01 | 送信ボタンは処理中に二重送信しない     |
| NFR-U02 | 必須項目とエラー理由をフィールド近くに出す |
| NFR-U03 | 削除は確認なしに実行しない         |


## 9. 制約

- 同時利用者は少なく、SQLite の書き込みロックは許容する。
- HTTPS は本番でリバースプロキシ終端を目指すが、学習段階の HTTP 公開はドキュメント上の暫定として明示する。
- Oracle Database は使わない。インフラが OCI であり、RDBMS は SQLite である。
