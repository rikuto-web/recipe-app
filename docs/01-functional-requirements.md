# 機能要件

## 1. 目的

レシピの作成・参照・更新・削除を、材料と手順を構造化した状態で行えるようにする。一覧では検索・フィルタ・並び替えができ、詳細では人数を変えたときの材料量を按分表示できる。

## 2. 対象ユーザー

認証は行わない。ブラウザからアクセスした **利用者** が、登録済みの全レシピを操作できる。

## 3. スコープ

### 3.1 対象

| ID | 機能 | 概要 |
| --- | --- | --- |
| FR-01 | レシピ一覧 | タイトル、カテゴリ、難易度、調理時間の要約を一覧表示する |
| FR-02 | 検索 | タイトルの部分一致で絞り込む |
| FR-03 | フィルタ / 並び替え | カテゴリ、難易度、調理時間の上限、新しい順などで絞り込む・並べる |
| FR-04 | レシピ詳細 | 説明、材料、手順を表示する。人数変更時は材料量を按分表示する |
| FR-05 | レシピ作成 | 親情報と材料行・手順行をまとめて登録する |
| FR-06 | レシピ更新 | 親情報を更新する。材料・手順は行単位で追加・修正・削除できる |
| FR-07 | レシピ削除 | 確認のうえ物理削除する。材料・手順も同時に削除する |
| FR-08 | カテゴリ参照 | シード済みカテゴリを選択・フィルタに使う |
| FR-09 | 入力チェック | 画面と API の両方で必須・形式・件数を検証する |

### 3.2 対象外（将来拡張）

| 項目 | 理由 |
| --- | --- |
| ログイン / ユーザー管理 | 初級範囲として認証基盤を扱わない |
| 画像アップロード | ストレージとコンテンツ配信が重くなる |
| カテゴリの CRUD | マスタはシードで足りる |
| タグ、コメント、お気に入り | 認証や追加エンティティが必要 |
| 栄養計算、買い物リストの永続化 | 本課題の中核ではない |

## 4. 詳細要件

### 4.1 レシピ本体

1 件のレシピは次を持つ。

| 項目 | 制約 |
| --- | --- |
| タイトル | 必須。1〜100 文字 |
| 説明 | 任意。0〜2000 文字 |
| カテゴリ | 必須。シード済み ID のいずれか |
| 人数（servings） | 必須。1 以上の整数 |
| 調理時間（分） | 必須。10 以上の整数。10 分単位（UI は ±10 分ステッパー） |
| 難易度 | 必須。1〜5 の整数（★1〜★5）。画面では星で表示する |

**難易度と星表示**

| 値 | 表示 | 目安 |
| --- | --- | --- |
| 1 | ★☆☆☆☆ | とても簡単 |
| 2 | ★★☆☆☆ | 簡単 |
| 3 | ★★★☆☆ | 普通 |
| 4 | ★★★★☆ | やや難 |
| 5 | ★★★★★ | 難しい |

API・DB では整数 1〜5 を保持し、一覧・詳細・フィルタでは星アイコンで表現する。

### 4.2 材料

- 1 レシピにつき 1 件以上。
- 各行は名前、分量、単位、並び順を持つ。
- 名前は必須（1〜100 文字）。分量は 0 より大きい数。単位は必須。
- **単位は決め打ちにしない。** 画面ではよく使う単位（`g`, `kg`, `ml`, `L`, `個`, `本`, `枚`, `小さじ`, `大さじ`, `カップ`, `適量` 等）を選択肢として提示しつつ、リストにない単位は自由入力できる。
- バックエンドは単位文字列（1〜20 文字）として受け取り、固定 enum にはしない。
- **材料は行単位で修正できる。** 1 行だけ直したいときに、材料リスト全体の作り直し（DELETE + INSERT）は行わない。
- 編集画面では、各材料行を個別に保存・削除できる。新しい材料行の追加も行単位で行える。
- 新規作成時のみ、初回登録として材料をまとめて送信する。

**材料の更新方式**

| 操作 | 方式 |
| --- | --- |
| 新規作成 | 親リクエストに材料配列を含めて一括登録 |
| 1 行の修正 | 材料 ID を指定して `PATCH`（部分更新） |
| 1 行の追加 | 材料追加 API |
| 1 行の削除 | 材料削除 API |
| 並び替え | 材料の `PATCH` で `sort_order` を更新 |

**DELETE + INSERT を採用しない理由**

材料を毎回全削除して再 INSERT する方式は実装は簡単だが、行 ID が毎回変わり、1 行だけ直す UX と合わない。手順と同様、編集時は行単位の `PATCH` を採用する。

### 4.3 手順

- 1 レシピにつき 1 件以上。
- 各行は手順番号と本文を持つ。本文は必須（1〜2000 文字）。
- **手順は行単位で修正できる。** 1 行だけ直したいときに、レシピ全体を作り直す必要はない。
- 編集画面では、各手順行を個別に保存・削除できる。新しい手順行の追加も行単位で行える。
- 新規作成時のみ、初回登録として手順をまとめて送信する。
- 手順番号の並び替え（上下移動）に対応する。

**手順の更新方式**

| 操作 | 方式 |
| --- | --- |
| 新規作成 | 親リクエストに手順配列を含めて一括登録 |
| 1 行の修正 | 手順 ID を指定して部分更新 |
| 1 行の追加 | 手順追加 API |
| 1 行の削除 | 手順削除 API |
| 並び替え | 手順の部分更新または専用 API で番号を更新 |

### 4.4 カテゴリ

シード例:

- 和食
- 洋食
- 中華
- デザート
- その他

利用者はカテゴリの追加・変更・削除を行わない。

### 4.5 一覧の検索・フィルタ

| 条件 | 仕様 |
| --- | --- |
| キーワード `q` | タイトルの部分一致。未指定なら全件 |
| `category_id` | 完全一致 |
| `difficulty` | 完全一致（1〜5。フィルタ UI は星選択） |
| `max_cook_time` | 調理時間が指定分以下。UI・URL パース時は 10 分単位に丸める（最小 10） |
| `sort` | `newest`（既定）または `cook_time_asc` |

条件は組み合わせ可能。ヒット件数は一覧に表示する。該当なしのときは空状態を出す。

### 4.6 人数の按分表示

- 詳細画面のみ。保存済みの `servings` を基準人数とする。
- 利用者が表示人数を変えると、各材料の分量を `表示人数 / 基準人数` 倍して見せる。
- 按分結果はデータベースに書かない。
- 基準人数より少なくしても 0 件にはしない。表示人数は 1 以上。

### 4.7 作成・更新の原子性

- **新規作成**: 親・材料・手順を 1 トランザクションで登録する。途中失敗時はすべて残さない。
- **レシピ更新（親のみ）**: 親情報の更新を 1 トランザクションで行う。
- **材料・手順の行単位操作**: 1 行の追加・更新・削除は、それぞれ 1 トランザクションで行う。他の行には影響しない。

### 4.8 削除

- 一覧または詳細から削除できる。
- 実行前に確認ダイアログを出す。
- 成功後は一覧へ戻る。
- **物理削除**とする。論理削除（削除フラグ）は行わない。
- 子レコード（材料・手順）は外部キーの `ON DELETE CASCADE` で DB から削除する。

### 4.9 バリデーションの分担

| 層 | 目的 |
| --- | --- |
| フロントエンド | 送信前に誤りを伝え、不要なリクエストを減らす |
| バックエンド | 画面を経由しないリクエストでも不正データを拒否する |

どちらか一方だけでは不十分とする。詳細は [非機能要件](02-non-functional-requirements.md) を参照。

**新規作成フォーム（SC-03）のクライアント側**

| タイミング | 挙動 |
| --- | --- |
| フィールドを触れた後（blur / 入力） | そのフィールドだけ検証。必須項目が空ならエラー表示 |
| 未触れの必須項目 | 保存までエラーにしない |
| 保存ボタン | 全フィールドを検証。エラーがあれば送信しない |
| 全角数字（分量等） | 半角に正規化してから検証・送信 |

サーバーが 400 `VALIDATION_ERROR` を返した場合は、レスポンスの `details[].field` をフィールド横に表示する。

### 4.10 エラー時の振る舞い

- ネットワーク障害や 5xx では、画面を止めずにメッセージを出す。
- 4xx（バリデーション、存在しない ID）では、原因が分かる文言を出す。
- 存在しないレシピへの詳細・編集は、一覧へ誘導する。
